## Summary

Every language surface now carries coherent, publish-ready packaging metadata at **version 1.3.1** (matching
the v1.3.x release-notes line), with installed CLIs for the three Python references and real install targets
for C/C++. **Nothing is published to any registry**: publication is gated on the name-clearance decision and
the posture is recorded in `docs/decisions/2026-06-10-distribution-posture.md`. A manual-dispatch
`release.yml` workflow re-runs the conformance gate, builds all four whitepapers and every distributable,
checksums them, and creates a **draft** GitHub release — its registry-publish stanzas are commented out and
explicitly gated.

## Migration

- **Installed CLIs:** `pip install -e tessera-id/python` (etc.) exposes `tessera-id` / `tessera-hash` /
  `tessera-seal` on PATH. The previously documented `python3 tessera-seal/python/cli.py ...` form keeps
  working.
- **C/C++ consumers:** `make install [PREFIX=...] [DESTDIR=...]` then
  `cc app.c $(pkg-config --cflags --libs tessera-id)`; vendoring stays equally supported.
- **No registry migration:** nothing was or is published; consumers stay on checkout/vendoring until the
  name-clearance gate opens (exact publish command sequence is in the posture record).

## Security considerations

No crypto, RNG, or wire change. Supply-chain surface: packaging metadata only — no new runtime dependencies
in any language. The `prepare` npm script executes `tsc` on git-install (standard, but worth knowing for
audit). `release.yml` introduces no registry credentials and grants `contents: write` to exactly one job
that creates a draft release; all actions are SHA-pinned.
