# 2026-06-10 — TESS-00016 — Structured + differential fuzzing for the decode surfaces

**Type:** sec (test infrastructure; one security finding surfaced — see Security considerations)
**Scope:** umbrella — new fuzz harnesses under `tessera-{id,hash,seal}/`, a cross-language
differential fuzzer under `tools/`, and an OSS-Fuzz enrollment memo. **No wire/API behavior
changes; no vector mutations.**
**Plan items:** TP-096 (decoder fuzzing), TP-097 (differential fuzzing oracle), OSS-Fuzz memo.

## Summary

Adds coverage-guided / structured fuzzing to the parser-heavy decode surfaces in three languages,
a cryptofuzz-style differential fuzzer that diffs all 8 conformance runners against the Python
oracle, and a gated OSS-Fuzz enrollment plan. The very first C fuzz run (60 s) found a real
**heap out-of-bounds read in the canonical C `tessera_seal_decrypt`** when an attacker sets
`KEM_CT_LEN` smaller than the ML-KEM-1024 ciphertext size — a pre-existing defect, now
characterized with a deterministic repro and handed off for a fix (it is **not** fixed in this
change; `tessera_seal.c` is outside this change's scope). Every other fuzz target ran its budget
clean and the 8-language differential run is clean over 200 structured inputs.

## Security considerations

**Finding (HIGH): heap out-of-bounds read in the C `tessera_seal_decrypt` (CWE-125).**
Reachable by any caller that passes attacker-controlled envelope bytes — the canonical use case.

- **Root cause:** `tessera_seal_peek_header()` validates only `kem_ct_len <= MAX_KEM_CT_LEN`
  (4096); it does **not** pin `kem_ct_len` to the suite-required ML-KEM-1024 ciphertext size
  (1568). `tessera_seal_decrypt()` then computes its `fixed` length floor using the
  attacker-controlled `h.kem_ct_len`, so an envelope with `kem_ct_len` **smaller** than 1568
  passes the `env_len >= fixed` check. `mlkem_decaps()` (`tessera_seal.c:333`) unconditionally
  reads `TESSERA_SEAL_MLKEM1024_CT_BYTES` (1568) bytes from `env + 16`, running up to ~1568 bytes
  past the envelope buffer.
- **Why existing KATs missed it:** `invalid.json` covers only `kem_ct_len` **larger** than the
  envelope (`wrong_kem_ct_len_valid_header` kem_ct_len=4096, `trunc_mid_kem_ct` truncated) — both
  caught by the length check. The **smaller-than-1568** direction was uncovered. The fuzzer hit it
  on the variant/suite-pinned pass.
- **Deterministic repro:** envelope = 76 bytes, `variant=0x04`, `suite=0x01`, `kem_ct_len=0`,
  `ad_len=0` → `tessera_seal_decrypt` reads ~1508 bytes past a tightly-sized buffer. Confirmed
  under ASan as `heap-buffer-overflow … READ of size 104 in keccak_update` via
  `ossl_ml_kem_decap` ← `mlkem_decaps tessera_seal.c:333` ← `tessera_seal_decrypt tessera_seal.c:728`.
  Repro bytes preserved at `/tmp/tessera_seal_c_oob_repro.bin` (878-byte campaign artifact).
- **Suggested fix (owner: TSEAL / C reference, NOT in this change):** before slicing/decaps,
  require `h.kem_ct_len == TESSERA_SEAL_MLKEM1024_CT_BYTES` for the non-hybrid suites (and the
  hybrid size once 0x06 lands in C) and return `TESSERA_SEAL_E_INVALID_LEN` otherwise — ideally
  in `tessera_seal_peek_header()` so `validate()`/`peek_ad()`/`decrypt()` all inherit it. Then
  append a `kem_ct_len_too_small_valid_header` record to `invalid.json` (append-only, freeze-safe)
  to lock the regression in across all languages.
- **Cross-language exposure:** the Go/Rust/Python references slice
  `env[16 : 16+kem_ct_len]` and hand that exact-length slice to a length-checked ML-KEM
  decapsulation, so they reject (or safely fail auth) rather than over-read; the defect is specific
  to the C reference's fixed-size `mlkem_decaps` read. (Confirm during the fix with a 4-language
  KAT once the new vector is appended.)

No secret-correlated timing change is introduced by the fuzz harnesses themselves; the finding is
a memory-safety bug, not a timing oracle.

## Rollback

Pure additive test infrastructure. To roll back: delete the new `*/rust/fuzz/` dirs, the two new
`*/go/fuzz_test.go` files, the added `tessera-id/go/testdata/fuzz/**` seeds,
`tessera-seal/c/fuzz_decrypt.c`, `tools/scripts/differential-fuzz.sh`,
`tools/conformance/DIFFERENTIAL.md`, the two docs, and revert the `tessera-seal/c/Makefile`
`fuzz*`/`clean` hunk. No wire artifacts, vectors, or shipped behavior depend on any of it; the
security **finding** stands independently of the harness and must be tracked to closure regardless
of rollback.
