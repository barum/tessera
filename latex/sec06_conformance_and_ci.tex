\section{Conformance and CI}
\label{sec:conformance}

\subsection{The hybrid suite \texorpdfstring{\code{0x06}}{0x06} skip discipline}

\tesseraseal{}'s hybrid suite \code{0x06} (TSEAL-00021, v1.2) is a polyglot KAT contract that some language ports have not yet caught up to as of v1.3. The harness filters \texttt{hybrid\_*.json} vector files per language via the \texttt{hybrid\_supported()} function in \texttt{tools/conformance/run.sh}:

\begin{lstlisting}[language=bash]
hybrid_supported() {
    case "$1" in
        python) return 0 ;;   # TSEAL-00021, v1.2
        rust)   return 0 ;;   # TSEAL-00028, v1.3
        go)     return 0 ;;   # TSEAL-00029, v1.3
        *)      return 1 ;;   # C / C++ / TS / Java / CPython ext: v1.4 backlog
    esac
}
\end{lstlisting}

Languages without hybrid skip the \texttt{hybrid\_*.json} files entirely and MUST reject suite \code{0x06} as \code{UNKNOWN\_SUITE} for any non-hybrid envelope they encounter. When porting hybrid to a new language: (i) implement hybrid in that language, (ii) update the language's conformance runner to accept 96-byte hybrid seeds (the standard runners hard-coded \texttt{len(seed) != 64}), (iii) flip the language's \texttt{hybrid\_supported()} entry, (iv) verify the language's PASS count rises by 9 (one per record across the three hybrid KAT files).

C++, TypeScript, Java, and the CPython extension have no \texttt{tessera\_seal\_runner} binary and \emph{skip} the TesseraSeal vector directory entirely --- there is \emph{no} Python-runner fallback for TesseraSeal (\texttt{tessera\_seal\_runner\_cmd} in \texttt{tools/conformance/run.sh} simply has no entry for those four languages). Their TesseraSeal conformance coverage begins when their v1.4 TesseraSeal ports land; their per-language suites cover TesseraID and TesseraHash directly today. SKIP counts are explicit, never silent: \texttt{doc} pseudo-records and records a language cannot execute emit \texttt{SKIP} lines that the harness reconciles against each file's record count.

\subsection{How CI gates the work}

\texttt{conformance.yml} is the only automatically triggered workflow in the repository: it runs on every pull request and every push to \texttt{main} (plus manual dispatch), and branch protection on \texttt{main} requires its \texttt{cross-language} job. Within that job the blocking step is the four-language alpha run (Python + C + Go + Rust --- the four ports with their own TesseraSeal runners); the full eight-language step is informational (\texttt{continue-on-error}) until the remaining TesseraSeal ports land. The ten other workflows (per-language matrices, \texttt{tessera-seal.yml}, \texttt{latex.yml}) are manual-dispatch only, for cost control. The harness is non-flaky by design: KAT vectors are deterministic, the per-language runners do not call out to the network, and the toolchains are pinned. A red harness means one of two things:

\begin{itemize}
\item A language port produced a different byte sequence for the same input. The port is wrong; fix the port.
\item The KAT vector itself changed. Shipped vectors are frozen append-only: regeneration MAY add records or files but MUST NOT mutate existing record bytes, and a mutated record fails the freeze check. A Python-reference behavior change is a spec change, requires a release-notes entry, and all other language ports must be updated to match before the PR merges.
\end{itemize}

The harness is what makes the spec-first methodology load-bearing. Without it, ``Python is right'' is just a slogan; with it, a language port that disagrees with Python is detectable in seconds.
