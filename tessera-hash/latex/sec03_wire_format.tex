\section{Wire Format (Normative)}
\label{sec:wire-format}

Big-endian throughout. \textbf{Total length: 73 bytes. Fixed.}

\begin{lstlisting}[language=Pseudocode]
Offset  Size  Field
------  ----  ---------------------------------------------------------
0       6     TS         (timestamp_ms, 48-bit big-endian unsigned)
6       1     VARIANT    (= 0x03 for TesseraHash v1)
7       2     COUNTER    (16-bit big-endian unsigned, monotonic per ms)
9       64    TAIL       (SHAKE-256(content, 64 bytes))
\end{lstlisting}

\subsection{Header (offsets 0--8)}

The 9-byte header is \emph{layout-identical} to \tesseraid{}'s header (\code{TS(6) || VARIANT(1) || CTR(2)}). The same 9-byte parser used in \tesseraid{} works on a \tesserahash{} for the timestamp, variant byte, and counter fields without modification. A shared C header at \texttt{common/c/tessera\_header.h} pins those offsets across all three \tessera{} projects (\tesseraid{}, \tesserahash{}, \tesseraseal{}).

\textbf{Timestamp.} 48-bit unsigned millisecond Unix timestamp. The field range is $[0,\ 2^{48}-1]$ ms --- 1970-01-01T00:00:00Z through approximately 10889-08-02 --- and standard decoders MUST accept the full range. Separately, and non-normatively, the constant \code{MIN\_TIMESTAMP\_MS = 1\_700\_000\_000\_000} ($\approx$ 2023-11-14, matching the analogous TesseraID constant) is a sanity gate exposed via the optional \code{validate\_min\_timestamp} helper: a generator that produces a timestamp before that gate is almost certainly running with a misconfigured clock. The helper is \emph{not} part of the wire contract; it exists for callers who want to cheaply reject obvious mis-parses at boundary entry points. Constructor-style APIs that accept an explicit timestamp (\code{hash\_at}, \cref{sec:generator}) MUST reject values outside $[0,\ 2^{48}-1]$ with an error rather than silently masking them to the field width.

\textbf{Variant byte.} \code{0x03} owns this project. Every other byte MUST be rejected at decode (\code{TESSERA\_HASH\_E\_UNKNOWN\_VAR}). This applies uniformly to the binary decoder \emph{and} to both canonical text decoders: the 98-character Base64URL and 117-character Crockford Base32 decoders MUST validate the variant byte after character-level decoding and reject any non-\code{0x03} value at decode time, rather than deferring the check to a separate validation step. The reserved-future range is shared monorepo-wide: \tesseraid{} owns \code{0x01}/\code{0x02}, \tesseraseal{} owns \code{0x04}; \code{0x00} and \code{0xFF} are permanently reserved; \code{0x05}--\code{0xFE} are reserved-future. Cross-project rejection --- in binary and in both text forms --- is gated by the \texttt{invalid.json} KAT files in every project's \texttt{conformance/vectors/} directory.

\textbf{Counter.} 16-bit unsigned, big-endian. The generator increments the counter monotonically within a millisecond; on a new millisecond it resets to 0. On counter exhaustion (more than $2^{16}$ \tesserahash{}es generated in the same millisecond by a single generator) the generator MUST spin until the wall clock strictly exceeds the last emitted timestamp (\code{now > last\_ts}), take that clock value as the new timestamp, and reset the counter to 0 --- the same spin-to-next-millisecond discipline used by \tesseraid{}'s Standard generator. If the wall clock reads \emph{earlier} than the last emitted timestamp (a backward clock jump), the generator clamps to \code{last\_ts} and continues in the same-millisecond branch; emitted timestamps never regress. Constructor-style APIs that accept an explicit counter (\code{hash\_at}, \cref{sec:generator}) MUST reject values outside $[0,\ \code{0xFFFF}]$ with an error rather than silently masking them.

\subsection{Tail (offsets 9--72)}

64 bytes of SHAKE-256 \citep{fips202} output computed deterministically from the input content. \tesserahash{} uses SHAKE-256 in its standard arbitrary-output-length mode with a fixed output length of 64 bytes (512 bits). The choice of SHAKE-256 over fixed-output SHA3-512 is deliberate: the same primitive is vendored in \texttt{common/c/keccak.\{h,c\}} for use by \tesseraseal{}'s HKDF-SHA3-256 construction, so the C, C++, and Java implementations of all three projects share a single audited Keccak source.

\subsection{Length and identifier-equality semantics}

Two \tesserahash{}es are \emph{content-equivalent} iff their 64-byte tails are identical. They are \emph{wire-equal} iff all 73 bytes are identical. Code that deduplicates content should compare bytes \code{9..73}; code that needs a generator-provenance view (e.g., ``which generator produced this identifier first?'') compares the full 73 bytes. The encodings (\cref{sec:encodings}) preserve both byte ranges.
