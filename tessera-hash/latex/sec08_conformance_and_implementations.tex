\section{Conformance and Reference Implementations}
\label{sec:conformance}

\tesserahash{} ships byte-identical reference implementations in eight languages, all consumed by the same cross-language KAT harness used by \tesseraid{} and \tesseraseal{}. The wire format is the contract; the per-language code is a reference.

\subsection{KAT vector files}

\texttt{tessera-hash/conformance/vectors/}:

\begin{itemize}
\item \texttt{tessera\_hash\_decode.json} --- 73-byte hex $\to$ \{variant, timestamp\_ms, counter, tail\_hex\}.
\item \texttt{tessera\_hash\_hash\_only.json} --- known content $\to$ known 64-byte SHAKE-256 tail.
\item \texttt{tessera\_hash\_encode\_b64.json}, \texttt{tessera\_hash\_decode\_b64.json} --- 98-char Base64URL round-trip.
\item \texttt{tessera\_hash\_encode\_crockford.json}, \texttt{tessera\_hash\_decode\_crockford.json} --- 117-char Crockford round-trip.
\item \texttt{tessera\_hash\_verify.json} --- positive (matching content) and negative (one-bit content flip) cases for \texttt{verify(raw, content)}.
\item \texttt{tessera\_hash\_invalid.json} --- malformed inputs: wrong length, invalid variant byte in binary form (incl.\ cross-project \code{0x01}/\code{0x02}/\code{0x04} and mid-range reserved bytes), wrong-variant \emph{text} forms (Base64URL and Crockford strings carrying non-\code{0x03} variants, pinning decode-time variant validation), non-canonical Base64URL/Crockford characters, padding-bit anomalies.
\end{itemize}

Vectors are generated against the Python reference (\texttt{tessera-hash/python/tessera\_hash.py}) by \texttt{tessera-hash/conformance/scripts/generate\_tessera\_hash.py}; the generator is deterministic given fixed inputs. Shipped vectors are frozen append-only: regeneration may add records or files but MUST NOT change existing record bytes.

\subsection{Cross-language runner}

\texttt{tools/conformance/run.sh} discovers per-language runners under \texttt{tools/conformance/} (one directory per language: \texttt{python}, \texttt{c}, \texttt{cpp}, \texttt{go}, \texttt{rust}, \texttt{typescript}, \texttt{java}, \texttt{cpython}) and executes each against the KAT files for the projects that language implements. All eight languages consume the \texttt{tessera-id} and \texttt{tessera-hash} vector directories --- every \tesserahash{} vector runs in all eight. Only the four languages with their own \texttt{tessera-seal} runners (Python, C, Go, Rust) additionally consume \texttt{tessera-seal/conformance/vectors/}; C++, TypeScript, Java, and the CPython extension skip that directory until their TesseraSeal ports land --- there is no Python-runner fallback. Exit code 0 means every runner passed every vector it ran. The harness runs on every pull request and push (\texttt{.github/workflows/conformance.yml}) and its cross-language job is a required branch-protection check on \texttt{main}.

\begin{lstlisting}[language=bash]
bash tools/conformance/run.sh
TESSERA_CONFORMANCE_SKIP="cpython java cpp typescript" bash tools/conformance/run.sh   # quick loop
\end{lstlisting}

\subsection{Tests that must keep passing in every language}
\label{sec:conformance:tests}

\begin{itemize}
\item SHAKE-256 KAT vectors (canonical Keccak test vectors): hash of known inputs produces known outputs.
\item Hash $\to$ Base64URL round-trip: exact 98-character length, no padding.
\item Hash $\to$ Crockford Base32 round-trip: exact 117-character length, confusable folding on decode.
\item Invalid-variant decode rejection: \code{0x00}, \code{0x01}, \code{0x02}, \code{0x04}, and \code{0x05}--\code{0xFF} are all rejected with \code{UNKNOWN\_VARIANT}. Rejection applies in binary form \emph{and} through both text decoders (98-char Base64URL, 117-char Crockford).
\item \code{hash\_at} range rejection: an out-of-range \code{timestamp\_ms} (above $2^{48}-1$) or \code{counter} (above \code{0xFFFF}) MUST produce an error, never a silently masked value.
\item Cross-language conformance: a \tesserahash{} produced in one language MUST decode byte-identical in every other.
\item Padding-bit guards: Base64URL final-character low-4-bits zero; Crockford final-character low-bit zero.
\item Counter monotonicity within a millisecond, including spin-to-next-millisecond on counter exhaustion and clamping on backward clock jumps.
\end{itemize}

\subsection{Benchmark methodology and reference numbers}
\label{sec:conformance:bench}

Benchmarks live under \texttt{tessera-hash/benchmarks/}. Coverage is deliberately minimal today (a Python + C harness; the remaining languages are backlog --- this paper does not claim per-language benchmark files exist). The harness measures four operations:

\begin{enumerate}
\item \texttt{hash\_only(content)} on a fixed 1 KiB content buffer.
\item \texttt{Generator.new(content)} including header construction.
\item \texttt{decode(raw)} on a fixed 73-byte input.
\item \texttt{verify(raw, content)} on matching content.
\end{enumerate}

TesseraHash throughput is dominated by SHAKE-256 sponge cost; the wire-format work (parsing, counter advance, Base64URL/Crockford coding) is negligible relative to Keccak. This paper intentionally publishes no point-in-time throughput numbers: consult the checked-in run outputs and methodology notes in \texttt{tessera-hash/benchmarks/} for measured figures, and treat any figure not accompanied by a checked-in run output as unverified.
