# TesseraSeal FIPS 140-3 deployment note

**Date:** 2026-06-10 · **Status:** decision record, **non-normative**. **Tickets:** TP-147 / TESS-00018.

TesseraSeal is a wire format with reference implementations — it is **not itself a FIPS-validated cryptographic
module**, and this note makes no validation claim for any TesseraSeal code. FIPS 140-3 validation attaches to the
underlying cryptographic module a deployment links against. This page records, per language, which pinned module that
is and what its validation posture actually is, so regulated adopters can assess procurement honestly
(CMVP: <https://csrc.nist.gov/projects/cryptographic-module-validation-program>).

## The short version

- The **C port** calls ML-KEM, AES-256-GCM, SHA-3/SHAKE-256, and HMAC through **OpenSSL 3.5+ `EVP` APIs**. Once the
  OpenSSL 3.5-series FIPS provider (3.5.4) completes its FIPS 140-3 validation — expected in the **2026–2027**
  window; track the CMVP modules-in-process list
  (<https://csrc.nist.gov/projects/cryptographic-module-validation-program/modules-in-process/modules-in-process-list>)
  — the C port inherits a validated module by configuring that provider. No TesseraSeal code change is anticipated.
- The **Python reference** uses `kyber-py` (<https://github.com/GiacomoPope/kyber-py>), which is **unvalidated** pure
  Python. Its role in this repo is **spec readability and KAT-vector generation**, not hardened production crypto;
  do not deploy the Python reference where FIPS validation is required.
- **Suite selection matters more than language**: in a FIPS-approved deployment only suite `0x01` qualifies.
  ChaCha20-Poly1305 (suite `0x02`) is not a FIPS-approved AEAD, and X25519 key establishment (inside hybrid suite
  `0x06`) is not approved under SP 800-56A rev. 3. ML-KEM (FIPS 203), AES-256-GCM (SP 800-38D), SHA-3/SHAKE-256
  (FIPS 202), and HMAC (FIPS 198-1) are all approved algorithms. This aligns with the strict CNSA profile in
  [policy-profiles.md](policy-profiles.md).

## Per-language validation posture (2026-06-10)

| Language    | Pinned ML-KEM source                  | FIPS 140-3 posture                                                |
|-------------|---------------------------------------|-------------------------------------------------------------------|
| C           | OpenSSL 3.5+ `EVP_PKEY` ML-KEM        | Pending: inherits OpenSSL's FIPS provider once the 3.5.4 validation completes (expected 2026–2027); requires the FIPS provider to be configured and approved-mode constraints honored |
| C++         | wraps the C library                   | Inherits the C/OpenSSL posture above                               |
| CPython ext | wraps the C reference                 | Inherits the C/OpenSSL posture above                               |
| Python      | `kyber-py` ≥ 1.0                      | **Unvalidated** — spec-readability / KAT-generation role only      |
| Go          | stdlib `crypto/mlkem` (Go 1.26+)      | Go's native FIPS 140-3 module (`GODEBUG=fips140=on`, Go 1.24+) places ML-KEM inside its module boundary and has been submitted to CMVP — check certificate status before relying on it (<https://go.dev/doc/security/fips140>). Note: the older `GOEXPERIMENT=boringcrypto` path does **not** provide ML-KEM and is not a route to FIPS ML-KEM |
| Rust        | RustCrypto `ml-kem` 0.3               | **Unvalidated**; no validation effort announced (<https://github.com/RustCrypto/KEMs>) |
| Java        | SunJCE JEP 452 (<https://openjdk.org/jeps/452>) | **Unvalidated** — the JDK's built-in providers are not FIPS-validated modules. Validated Java options exist only via third-party providers, which the supply-chain pin in [../CLAUDE.md](../CLAUDE.md) forbids without an explicit security review |
| TypeScript  | `@noble/post-quantum` (<https://github.com/paulmillr/noble-post-quantum>) | **Unvalidated** (independently audited, but no CMVP validation)    |

Non-KEM primitives follow the same logic: in C they come from the same OpenSSL provider (so the FIPS story is
uniform); in Go from the same stdlib module boundary; elsewhere from the per-language pinned sources in the
[../CLAUDE.md](../CLAUDE.md) supply-chain table, none of which are validated modules.

## Deployment checklist for a FIPS-constrained adopter

1. Use the **C port** (or C++/CPython wrappers over it) linked against OpenSSL 3.5+ with the FIPS provider active,
   once the 3.5-series validation is granted — verify the certificate on the CMVP list first.
2. Restrict envelopes to **suite `0x01`**. Reject `0x02` (non-approved AEAD) and `0x06` (non-approved classical KEM
   component) at policy level; the decoder-level suite checks already enforce unknown-suite rejection.
3. Treat the Python reference and the conformance harness as **test tooling**: KAT vectors generated by `kyber-py`
   verify wire correctness, and that role does not require validation.
4. Re-check this table before procurement conversations — validation status is time-dependent and this page is a
   dated snapshot, not a live feed. The 2027 CNSA acquisition expectations
   ([policy-profiles.md](policy-profiles.md)) make the C/OpenSSL path the default answer for US-regulated buyers.
