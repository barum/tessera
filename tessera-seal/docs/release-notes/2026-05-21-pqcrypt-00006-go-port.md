# PQCK-00006 — PQCrypt Go port

**Date:** 2026-05-21
**Ticket:** PQCK-00006
**Type:** feat

## Summary

Ship the Go reference implementation. Uses Go 1.26's stdlib `crypto/mlkem` for ML-KEM-1024 (no `filippo.io/mlkem` dependency needed); `golang.org/x/crypto/sha3` for SHA3/SHAKE; `crypto/aes` + `cipher.GCMWithNonceSize` for AES-256-GCM; `golang.org/x/crypto/chacha20poly1305` for the optional ChaCha suite. ~70 tests pass, all KAT vectors consume identically to Python and C, **cross-language interop confirmed in both directions**.

## Wire/API changes

No wire-format change. Two artifact changes:

1. **Python module** (`pqcrypt/python/pqcrypt.py`): new public `generate_keypair_from_seed(seed, suite)` plus `KEYPAIR_SEED_BYTES = 64`. Existing `generate_keypair()` is unchanged.
2. **Conformance vectors**: every record carrying a private key now emits both `private_key_seed_hex` (64-byte FIPS 203 seed, d || z) and `private_key_hex` (3168-byte expanded form). C and Rust consume the expanded form; Go consumes the seed via `mlkem.NewDecapsulationKey1024(seed)`. Vectors remain byte-deterministic across regenerations.

## Migration guidance

Existing Python and C consumers do not need changes. Vector schema gained the additive `private_key_seed_hex` field; existing parsers can ignore it.

For new Go consumers:

```go
import "pqcrypt"
priv, pub, _ := pqcrypt.GenerateKeypair(pqcrypt.SuiteMLKEM1024AESGCM)
env, _      := pqcrypt.Encrypt([]byte("payload"), pub,
                               pqcrypt.SuiteMLKEM1024AESGCM,
                               []byte("pqid-as-ad"), 0, 0)
pt, _       := pqcrypt.Decrypt(env, priv, []byte("pqid-as-ad"))
```

**Cross-language interop verified:**

1. **Python → Go**: all 13 KAT decrypt records consume successfully via the seed-form keypair reconstruction.
2. **Go → Python**: a Go-produced 1689 B envelope (16-byte AD) decrypts byte-identical in Python through `generate_keypair_from_seed(seed)`.
3. **C ↔ Go (transitive)**: both decode the same Python-generated envelopes to the same plaintext.

## Rollback

`git rm -r pqcrypt/go`, revert `go.work`, revert the `generate_keypair_from_seed` addition (or keep — it's additive), regenerate vectors without `private_key_seed_hex` (or keep — additive and ignored by other languages).

## Security considerations

- **`crypto/mlkem` from stdlib** — Go 1.24+ ships ML-KEM-512/768/1024. Constant-time decapsulation documented by Go security team. No external ML-KEM dependency.
- **AES-256-GCM via `crypto/cipher.GCMWithNonceSize(12)`** — AESNI on x86-64, ARMv8 crypto extensions on Apple Silicon. Tag verification is constant-time inside `cipher.AEAD.Open`.
- **`hmac.Equal` constant-time compares** — for nonce, AD, and commit-tag verification.
- **Synthetic-key timing pad** — `deriveSyntheticKeys()` runs on the structural-failure path to keep decrypt-path timing flat. Mirrors C and Python.
- **No "Kyber" naming** in the public surface — Go stdlib uses `mlkem.*` uniformly; this package re-exports as `MLKem1024*`.
- **Seed exposure caveat** — `PrivateKey.Seed()` returns the 64-byte seed. Production deployments should keep it in HSM/SE; we do not promise garbage-collected zeroization (mirrors the Python reference caveat).
