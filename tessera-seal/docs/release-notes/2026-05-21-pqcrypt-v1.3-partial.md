# PQCK-00027..00029 — PQCrypt v1.3 (partial: Rust + Go hybrid)

**Date:** 2026-05-21
**Scope:** v1.3 partial release. Hybrid suite `0x06` ports from Python-
only (v1.2) to Python + Rust + Go (v1.3). C / TypeScript / Java / CPython
ext hybrid ports remain v1.4 work.
**Status:** released

## Summary

The post-v1.2 hardening cycle landed three follow-up tickets today:

- **PQCK-00027** investigated enabling ARMv8 AES intrinsics for Rust's
  AES-256-GCM 1 MiB throughput. The `aes-gcm 0.10` `aes` feature alone
  does not enable ARMv8 intrinsics on stable Rust. Two viable paths:
  upgrade to `aes-gcm 0.11` (when released) or use a nightly
  `target_feature` cfg. **Deferred to v1.4.**
- **PQCK-00028** ported hybrid suite `0x06` (X25519 + ML-KEM-1024 +
  AES-256-GCM + UtC) to Rust using `x25519-dalek` 2.x.
- **PQCK-00029** ported the same to Go using stdlib `crypto/ecdh` X25519
  (no external dep needed).

Three of four v1 alpha languages now have hybrid coverage. C / TS / Java
/ CPython ext follow in v1.4 (PQCK-00031..00034).

0.11` ships).

## Migrations

None. Suite `0x06` allocation remains additive. A v1.2 deployment of any
non-Python language rejects hybrid envelopes as UNKNOWN_SUITE; a v1.3
Rust or Go deployment decrypts byte-identical to Python.

## Rollback

`git revert` PQCK-00028 and/or PQCK-00029 commits independently. Both are
purely additive. Existing v1.0–v1.2 envelopes remain byte-identical
across the rollback boundary.

## Security considerations

- Both hybrid ports preserve the OS-CSPRNG-only invariant for ML-KEM
  Encaps randomness and X25519 ephemeral key generation.
- Both ports add suite/key-mismatch checks at the API boundary (matching
  Python).
- Side-channel posture unchanged: software timing only, per
  `pqcrypt/docs/side-channel-disclaimer.md`. `x25519-dalek` and
  `crypto/ecdh` are both constant-time on the scalar multiplication.
- Combiner is identical to Python (whitepaper §sec05) — verified by
  byte-identical KAT consumption.
